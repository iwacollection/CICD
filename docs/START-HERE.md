# 第一次看这个 CI/CD 项目：从这里开始

> **先别从头读完整个 docs 目录。** 这个仓库已经积累了很多专题文档，它们是给不同问题查阅的，不是要求一次全部学完。
>
> 如果你是第一次理解这套平台，只需要先看本页，再按下面的 4 步走。

## 先用一句话理解它

这套平台要解决的事情是：

**把开发人员提交的代码，安全、稳定地变成可以发布的软件，并且能证明发布的是什么版本；发布出问题时，可以退回之前验证过的版本。**

可以把它理解成软件工厂：

| 软件工厂里的事情 | CI/CD 平台里对应的事情 | 简单解释 |
|---|---|---|
| 接收订单和原材料 | 项目配置、代码提交 | 知道要构建哪个项目、使用什么代码 |
| 选择生产设备 | Toolchain 工具链 | 选择固定版本的 JDK、编译器、构建环境 |
| 安排生产顺序 | DAG 依赖关系 | 先生产被依赖的组件，再生产依赖它的组件 |
| 生产并检查产品 | Build、Test | 编译软件并执行测试 |
| 给产品贴唯一编号 | Artifact Contract | 记录制品来源、版本、依赖和校验值 |
| 质量检查和入库 | 安全扫描、SBOM、签名、Archive | 检查风险并保存可追溯的制品 |
| 把同一件产品送到不同环境 | Promotion | 同一个制品依次进入测试、预发布、生产 |
| 出问题时退回上一件合格产品 | Rollback | 恢复以前保存的制品，不重新编译 |

## 建议按这个顺序学习

### 第 1 步：先看全貌，不要钻代码

阅读：[总体架构](architecture.md)

只需要回答三个问题：

1. 代码从哪里进入平台？
2. 平台经过哪些主要环节？
3. 最后生成什么东西？

读完后，你应该能说清楚：

`代码 → 构建 → 测试 → 制品 → 安全检查 → 归档 → 发布 → 回滚`

暂时不需要理解每个 Python 脚本和每个 GitHub Actions 文件。

### 第 2 步：理解为什么要安排构建顺序

阅读：[真实依赖 DAG](dependency-dag-execution.md)

先记住一个例子：

- A 是公共基础库；
- B 使用 A；
- C 使用 B。

那么不能随意先构建 C。平台必须先完成 A，再把 A 的构建结果交给 B，最后再交给 C。

这里的 DAG 可以先理解为**带有依赖关系的任务顺序表**。同一层互不依赖的任务可以并行执行；有依赖的任务必须等待上游完成。

### 第 3 步：理解构建结果如何被证明

阅读：[Artifact Contract v2](artifact-contract-v2.md)

先把 Artifact 理解为“构建出来的软件包”，例如 JAR、二进制文件或固件。

平台不能只保存一个文件，还要记录：

- 它来自哪个仓库、哪个提交；
- 使用哪个工具链和构建环境；
- 依赖了哪些上游组件；
- 文件本身的 SHA256 校验值是什么。

这样才能避免“测试的是一个包，生产发布的却是另一个包”。

### 第 4 步：理解发布和回滚

阅读：[制品、晋级与回滚](artifacts-promotion-and-rollback.md)

重点只看懂这一条：

`构建一次 → 保存制品 → 测试环境验证 → 预发布验证 → 生产发布`

发布到不同环境时，使用的是**同一个制品**，而不是每到一个环境就重新编译一次。

如果生产出现问题，回滚是重新指向之前验证过的制品，不是临时重新构建一个“旧版本”。

这里说的是**业务制品晋级**，不是工具链镜像晋级，也不是 Kubernetes 实际部署。工具链镜像从 Candidate 进入 Active，要另看[工具链 Candidate 晋级操作手册](toolchain-promotion-runbook.md)。集群是否运行了目标镜像，则要看[Argo CD / Kubernetes 部署后运行验证](argocd-kubernetes-runtime-verification.md)。

## 先认识这 8 个常见词

| 词 | 先这样理解 |
|---|---|
| CI | 持续集成：代码提交后，自动编译、测试和检查 |
| CD | 持续交付/部署：把通过检查的软件安全地交付或发布 |
| Runner | 真正执行构建任务的机器或容器 |
| Toolchain | 工具链：编译器、JDK、Maven 等构建工具及其固定版本 |
| DAG | 任务依赖图：规定谁必须先完成、谁可以并行 |
| Artifact | 制品：构建后真正要保存、交付和发布的软件文件 |
| SBOM | 软件成分清单：列出软件包里包含哪些依赖组件 |
| GitOps | 用 Git 中声明的配置管理目标环境状态，并由控制器执行同步 |

理解主流程后，再按实际工作需要深入以下专题：

- [可复现构建门禁](reproducibility-gate.md)：如何验证相同源码和工具链能否产生一致的构建结果。
- [新项目接入手册](onboarding.md)：把一个真实业务项目接入平台时，逐项准备什么、如何验收。

不要把这些能力理解成额外的、互不相关的流水线。它们分别补足主流程中的质量检查、环境可信、构建可信和项目接入。

## 当前项目做到哪里了

请注意区分“仓库代码已经实现并通过自动化测试”和“已经接入真实企业生产环境”：

- 普通应用构建、依赖 DAG、制品校验、供应链检查和发布状态管理：仓库内已有实现及自动化验证。
- 生产生命周期验收记录中的 `dev`、`staging`、`production`，指 GitHub Deployment / 制品晋级记录中的环境名称；它证明制品身份、晋级顺序和历史 digest 回滚流程已执行，不代表已经向真实企业 Kubernetes 集群部署或切换用户流量。
- Java 17 和 Java 21：当前中央目录均登记为 Candidate，不能作为 Active 工具链供正式业务消费。Java 21 最近一次晋级运行在扫描报告 evidence hash 校验处失败，未进入独立审批；具体运行证据和边界见[工具链 Candidate 晋级操作手册](toolchain-promotion-runbook.md)。
- Jenkins Shared Library：仓库代码和 Mock Pipeline 测试已实现；**尚不能据此认定企业 Jenkins Controller / Agent 已完成真实接入验收**。
- Harbor：当前已验证链路使用 GHCR，企业 Harbor 的真实接入和扫描闭环仍需单独验收。
- Argo CD / Argo Rollouts：仓库已有接入契约、策略和验证代码；**不代表已经连接真实生产集群并执行发布**。
- RK 真机、高通和联发科：必须拿到真实 Runner、SDK、License 和硬件后才能完成物理验收。

文档的维护范围和当前审核状态见[技术文档审核记录](documentation-review.md)。
